一、先把两个项目的“30 秒版本”背下来
项目一：RAG

面试官：

介绍一下你的 RAG 项目。

你可以直接说：

我做的是一个多来源知识库问答系统，主要解决传统 Dense Retrieval 在复杂查询下召回不充分的问题。

在检索侧，我设计了 BM25 + BGE-M3 Dense Retrieval + RRF + Cross-Encoder Rerank 的多阶段检索链路，通过稀疏和稠密检索互补，再进行结果融合和重排序。

我还基于 LangSmith 构建了 50 条样本的评测集，从 Correctness、Relevance、Groundedness 和 Retrieval Relevance 等维度对不同方案进行对比，最终回答正确率超过 90%，相比单一 Dense Retrieval 提升约 10%。

在工程上，我使用 PostgreSQL + pgvector 存储文档 Chunk 和向量，通过 FastAPI + React 实现知识库和聊天功能，并加入多会话、短期记忆和长期记忆，同时使用 SSE 实现流式输出，最后通过 Docker 完成部署。

这段控制在 40～50 秒。

二、RAG 项目面试官最可能追问什么
1. 为什么不用单纯的向量检索？

这是非常大概率的问题。

不要说：

Dense Retrieval 效果不好。

应该说：

Dense Retrieval 更擅长处理语义相似的问题，但对于关键词、专有名词、编号、精确术语这类查询，BM25 往往更有优势。所以我采用稀疏检索和稠密检索结合的方式，让两者互补。

然后举例：

用户：
“RTX 4090 的显存是多少？”

Dense：
可能召回 GPU、RTX 系列相关内容

BM25：
“RTX 4090”精确匹配能力更强

所以：

BM25
+
Dense
=
互补召回
三、为什么还需要 RRF？

面试官可能继续：

BM25 和 Dense 都召回了，为什么不用分数直接相加？

回答：

因为 BM25 和 Dense Retrieval 的 score 并不处于同一个数值空间，直接加权比较并不稳定。所以我使用 RRF，根据不同检索方法中的排名位置进行融合，而不是直接比较原始分数。

核心公式其实记住思想就行：

RRF(d) = Σ 1 / (k + rank(d))

不用强行背公式。

面试时说：

RRF 主要解决不同 Retriever 的分数不可直接比较的问题，通过 rank 融合结果。

就够了。

四、为什么 RRF 后面还要 Rerank？

这个也非常容易问。

你的链路：

BM25
   +
Dense
   ↓
RRF
   ↓
Cross Encoder

解释：

BM25 + Dense + RRF 主要解决“尽可能召回正确文档”的问题，属于 Recall 阶段；Cross-Encoder Rerank 则对 query 和候选文档进行更精细的交互建模，重点提升 Top-K 的排序质量。所以我把它放在召回之后做二次排序。

一句话记：

前面负责“找得全”，Rerank 负责“排得准”。

这个非常适合面试。

五、你的 RAG 评测怎么讲？

这是你项目里很有价值的一部分。

面试官：

你怎么证明你的检索优化真的有效？

不要说：

我感觉效果更好了。

直接：

我用 LangSmith 构建了 50 条测试样本，对 Dense、BM25、Hybrid、RRF、Rerank 等方案进行对比，从 Correctness、Relevance、Groundedness、Retrieval Relevance 等维度评测，最终完整链路回答正确率超过 90%，相比单一 Dense Retrieval 提升约 10%。

然后面试官可能追：

Groundedness 和 Correctness 有什么区别？

你可以答：

Correctness 更偏向最终答案是不是正确；Groundedness 更关注答案是否能被提供的检索上下文支持，也就是有没有出现模型脱离检索结果自行生成的情况。

这个回答很好，因为说明你不是只会“跑 LangSmith”。

六、为什么需要 Groundedness？

可以继续回答：

RAG 的问题不只是“答错”，还可能是“看起来答对了，但是依据不在检索结果里面”。Groundedness 可以帮助我识别这种幻觉问题，所以不能只看最终答案的 correctness。

这就是一个比较成熟的回答。

七、为什么 PostgreSQL + pgvector？

面试官：

为什么不用 FAISS？

回答最好从“项目需求”出发，而不是说“pgvector 更高级”。

FAISS 更适合纯向量检索和本地实验，而我的项目除了向量，还需要保存用户文档、Chunk、会话、消息以及其他关系型数据，所以我选择 PostgreSQL + pgvector，把结构化数据和向量数据放在同一个数据库中，减少系统复杂度，也方便做持久化和业务关联。

然后：

PostgreSQL 本身负责关系型数据管理，pgvector 提供向量存储和相似度搜索能力。

八、SQLAlchemy 面试怎么讲？

你刚刚专门补了 SQLAlchemy，所以这一块要会讲。

面试官：

SQLAlchemy 在项目里面干嘛？

回答：

SQLAlchemy 主要作为 ORM 层，负责数据库模型和业务代码之间的映射。我用它管理用户文档、Chunk、Conversation、Message、Memory 等数据模型，减少直接拼接 SQL，同时方便做表之间的关联和 CRUD 操作。

如果追问：

ORM 和直接 SQL 有什么区别？

说：

ORM 用 Python 对象映射数据库表，可以提高业务代码的可维护性；但对于一些复杂查询或者性能敏感操作，我也可以直接使用 SQL。

这个程度够了。

九、你的 Memory 怎么讲？

你这个项目的 Memory 不要讲得太玄。

直接拆成：

短期记忆
+
长期记忆
短期记忆

保存当前会话最近几轮消息，作为当前上下文的一部分提供给模型。

长期记忆

从历史对话中提取相对稳定的用户信息，例如偏好、习惯，然后持久化保存；后续对话时再检索并注入上下文。

面试官如果问：

为什么不把所有历史消息都塞给 LLM？

答：

一方面上下文长度有限，另一方面历史消息越多，Token 成本和噪声都会增加。所以短期记忆保留近期上下文，长期记忆提取相对稳定的信息，减少无效历史信息。

这个回答很好。

十、RAG 项目的一个“难点”怎么说？

推荐你说：

我遇到的一个比较明显的问题是单一 Dense Retrieval 在一些关键词敏感的查询上召回不够稳定。后面通过 BM25 增加关键词匹配，再用 RRF 融合两个召回结果，最后通过 Cross-Encoder 做二次排序。同时为了避免“优化后只是主观感觉变好”，我又用 LangSmith 建了评测集做对比实验。

这就形成完整故事：

这比“我用了 BM25”高级很多。
